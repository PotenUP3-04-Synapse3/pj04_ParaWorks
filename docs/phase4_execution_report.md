# Phase 4: 하드코딩 제거 및 동적 대시보드 로직 구현 실행 보고서

본 문서는 **프로젝트 중심 지식 자동화 계획서**의 마지막 단계인 '동적 대시보드 로직 개편' 기능 구현 및 검증 결과를 기록합니다.

---

## 1. 작업 내용 (Action)

### 1.1 동적 프로젝트 대시보드 (Dynamic Project Memory) 개편
*   **변경 파일**: `backend/app/projects/service.py`
*   **작업 내용**:
    *   기존에 소스 코드에 하드코딩된 `CANONICAL_PROJECTS` 리스트를 기준으로만 데이터를 취합하던 방식(Hardcoding)을 폐기했습니다.
    *   이제는 DB에 저장된 `ReviewItem` 및 지식 모델(Phase 3에서 추가된 `project_key` 활용)들을 모두 스캔하여 **실제 승인된 데이터가 한 건이라도 존재하는 모든 프로젝트 키(`active_project_keys`)**를 동적으로 수집합니다.
    *   수집된 프로젝트 키가 기존 `CANONICAL_PROJECTS`에 있다면 해당 메타정보(이름, 요약)를, 없다면 AI가 생성한 '동적 프로젝트'임을 알리는 기본 메타정보를 함께 반환합니다.
*   **가치**: 
    *   AI가 새로운 주제를 발견하거나, 사용자가 임의의 `project_key`를 입력하여 승인하더라도 백엔드 코드의 배포나 수정 없이 대시보드 화면(프로젝트, 타임라인 탭)에 자동으로 새로운 프로젝트 탭이 나타나게 됩니다.

### 1.2 타임라인 연결 최적화
*   **작업 내용**:
    *   `_timeline_for_project` 함수가 타임라인 항목을 가져올 때 기존에는 복잡한 링크/소스 교집합 비교를 수행했으나, 이제는 명시적으로 부여된 `item.project_key == project_key` 조건을 통해 훨씬 빠르고 정확하게 필터링하도록 로직을 단순화 및 최적화했습니다.

---

## 2. 시행착오 및 해결 과정 (Mistakes & Troubleshooting)

*   **테스트 코드의 정적 의존성 문제**:
    *   **상황**: 비즈니스 로직을 동적으로 개편한 뒤 테스트(`test_projects_api_returns_two_canonical_projects_and_approved_evidence_only`)가 실패했습니다.
    *   **원인**: 테스트 코드 자체가 예전의 하드코딩된 '고정 프로젝트 2개 반환' 정책을 가정하고 작성되어 있었기 때문입니다. 실제로 바뀐 로직에서는 증거 데이터가 없는 `seed-ir` 프로젝트는 노출되지 않고, 증거가 삽입된 임의의 프로젝트(`project-newbiegenie`)가 노출되는 정상적인 동적 반응이 일어났습니다.
    *   **해결**: 시스템이 정상적으로 동적 작동함을 확인했으므로, 테스트 코드의 단언(Assertion) 구문을 동적 작동 방식에 맞게 수정(`'project-newbiegenie'`가 포함됨을 검증)하여 성공적으로 패스시켰습니다.

---

## 3. 검증 결과 (Validation)

동적으로 데이터를 수집하고 최적화된 조건으로 타임라인을 조회하는 API가 정상 작동하는지 자동화 테스트를 통해 확인했습니다.

*   **실행 명령어**: `uv run pytest backend/tests/test_project_memory_api.py -v`
*   **테스트 결과**: 5개 항목 모두 통과 (100% Passed)
    *   AI 자동 분류기가 정의된 규칙과 제외 규칙을 준수하는지 검증: 정상
    *   프로젝트 API가 승인된 동적 증거 데이터만을 기반으로 프로젝트를 구성하고, 타임라인을 연결하는지 검증: 정상
